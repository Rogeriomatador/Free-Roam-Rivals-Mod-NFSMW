# Evidence report: owner's 60-address Ghidra MCP batch (18 Oct 2026)

## Provenance and limits

One user-supplied local ZIP `ghidra_bulk_20261018-124310-961005.zip`
generated by `tools/ghidra_bulk_research.py`. Its manifest records:

- Ghidra x86/32bit **speed.exe**, apparent base `00400000`,
  **26,067 functions** and 72,577 symbols identified by the analyzer;
- disk game executable: **6,029,312 bytes**, MD5
  `C0516B485065FABDD69579816B5DF763`;
- **23 curated seeds**, 37 related addresses reached, max 1 callgraph hop;
- **60 addresses queried**, plus 35 pending queue entries not visited;
- **28 decompilation attempts, 22 successfully returned pseudocode**.
  Six results were `{"error":"No function found for ..."}` despite the
  original tool displaying `decompiled: 28, errors: 0`.
- All results are static Ghidra MCP reads; ZIP was produced locally.
  The manifest explicitly says that imported Ghidra program bytes were NOT
  independently validated against the on-disk MD5.
- The ZIP itself and proprietary decompiler pseudocode are **not** committed.

This corrects a tool-reporting defect, not an ASI behavior defect. The
collector now records embedded MCP response errors, counts genuine
decompilations, and skips function graph entries that MCP cannot resolve.

## Newly supported callgraph / vtable observations

1. **AIVehicleRacer host construction**. `0x0043F040` appears to
   allocate **0x7EC** bytes before calling initializer `0x0043EF70`,
   which installs primary vtable `0x00892AD0`; initializer calls
   `0x0043D330`. Xref at `0x00884237` is **DATA**.
   No direct function caller was identified by `get_function_callers`.
2. **AIGoalRacer construction**. `0x0043D400` appears to allocate
   **0x7CC** bytes before calling `0x0043D330`, which installs
   vtable `0x00892720` and uses the string `AIGoalRacer`.
   Xref `0x00884337` is **DATA**. Neither allocation wrapper by itself
   creates a persistent physical rival in Free Roam.
3. **Host per-frame dispatch**. `0x0042F140` is referenced by a
   **DATA** xref at `0x00892AF8`, an offset of **+0x28** from the
   primary Racer vtable `0x00892AD0`. It calls
   `0x004293D0` and `0x0042AA80`, and invokes game interfaces.
   It checks an object field at **+0x7CC** and a global state flag
   `DAT_0090D5FA`, and has conditional early/normal paths.
   This is consistent with Racer host tick, but never proves the
   freeroam scheduling/attachment or observed AI movement on its own.
4. **Goal per-frame dispatch**. `0x0042AA80` is referenced at
   `0x00892748` (= goal vtable `0x00892720` **+0x28**).
   Its body calls `0x004293D0` and conditionally invokes a virtual
   operation at offset **+8** of the goal object held by **+0xB8**.
   This is consistent with an active goal update, not indisputable
   proof of the ABI, ownership or sequence of game callbacks.
5. **Goal replacement**. `0x00422480` compares desired goal hash
   against `+0xC4`, conditionally invokes cleanup on the prior
   goal at `+0xB8`, uses a goal-factory linked list rooted at
   `DAT_0090D8E8`, and installs new goal at `+0xB8`.
   The observations support lifecycle complexity, not a diagnosis of
   the Rico handle transition.
6. **Pursuit/context sensitivity**. `0x004293D0` has callers
   `0x0042F140` and `0x0042AA80`, reads race/pursuit-related state
   `DAT_009B3829` and various vehicle/physics interfaces. This is a
   plausible locus for in-race vs freeroam divergence, but there is
   no identified path linking it to `ISimable::_mHandle` writes.
7. **Physical PVehicle constructor candidate**. `0x00689020` did
   return decompilation; it initializes many vehicle fields and mutates
   registries/global vehicle bookkeeping including `DAT_0092C514`
   and `DAT_0092CD24`. This is not enough to infer safe construction,
   stable ownership, destructor, streaming cleanup or cross-list identity.

## Rico: diagnosis remains open

The prior in-game logs recorded a changed
**`ISimable::_mHandle` while both registries still contained the
observed vehicle object**. This static batch does **not** identify who
writes the handle, when its associated object is invalidated, whether
the engine streams, rebinds or replaces a simable, or why an AI goal
would terminate. Distinguish:
- physical PVehicle still registered;
- AI host/goal still live and attached;
- ISimable identity current and synchronized;
- world generation / streaming and race transition;
- ownership and a verified cleanup callback.

**Do not** rewrite `_mHandle`, force a kill, spawn duplicates, or
change the runtime guard merely because the host/goal path has been mapped.
